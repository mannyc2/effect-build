## Product boundary

v0.5 keeps provider-native operations, adds two closed portable products, and
adds one separate closed Apple distribution track:

| Product                    | Exact identifier                                    | Release claim                                                                                                                       |
| -------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Node main                  | `effect-build/profile/node-main@1`                  | One sealed CommonJS or ESM main can be assembled into a Node 26.7.0 SEA only for evidence-backed targets.                           |
| Static browser application | `effect-build/profile/static-browser-application@1` | One explicit module application can be published as a complete immutable generation and exercised in Chromium, Firefox, and WebKit. |
| Apple direct distribution  | `effect-build-apple`                                | Explicit immutable artifacts can pass Developer ID signing, Apple container, notarization, stapling, and assessment transitions.    |

The classification vocabulary has five states. The fifth is necessary because
provider-authoritative graph analysis can discover a forbidden import or an
unknown edge only after provider work, while publication must still remain
untouched.

| Disposition                            | Boundary                                                                                                                    |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Admitted                               | A request may start provider work, or an analyzed result may be sealed or committed.                                        |
| Rejected before provider work          | The public request itself violates the profile.                                                                             |
| Rejected after analysis, before commit | Provider evidence proves the output violates the profile; no snapshot is lent, generation sealed, or destination activated. |
| Provider-native only                   | The native lane may accept it, but it earns no portable result.                                                             |
| Unsupported                            | Required provider, target, provenance, metadata, or runner evidence does not exist.                                         |

There is no silent narrowing or fallback between these states.

### Node main

The portable request admits exactly one opaque sealed main in CommonJS or ESM
format. It permits literal Node built-ins and forbids assets, plugins, snapshots,
code cache, package or local imports, JSON imports, dynamic import,
`createRequire`, computed loaders, native addons, `process.dlopen`, and runtime
code loading through `eval` or `new Function`.

The intended producer cells are Bun 1.3.14, esbuild 0.28.2, and Rolldown 1.2.5.
The assembler is Node 26.7.0. The accounted target universe is exactly:

- macOS x64 and arm64;
- Linux x64 and arm64 with the GNU ABI; and
- Windows x64 and arm64.

The exact official archive names and SHA-256 values are frozen in the machine
contract from Node's
[`SHASUMS256.txt`](https://nodejs.org/dist/v26.7.0/SHASUMS256.txt). Admission
requires its detached signature, the exact signer fingerprint, and the signer
key from the pinned `nodejs/release-keys` commit frozen in that contract. These
are evidence coordinates, not advertised support. Node 26.7.0 direct
`--build-sea` on macOS x64 is an explicit rejected target: Node's platform
support table skips it, upstream issue #65479 reproduces the same crash, and the
exact repository runner failed with `SIGSEGV`. The other five targets are
applicable. The contract therefore accounts for the complete 180-coordinate
Cartesian universe as 150 required positive receipts plus 30 explicit macOS x64
rejections. A positive cell becomes advertisable only after authenticated-
manifest admission, independent PE/ELF/Mach-O inspection, and an exact-target
execution receipt. There are no Node musl cells in this profile.

Every cross-built intermediate remains private until its exact-target runner
finalizes and rehashes it. Only then does that runner mint and return the one
`AssembledExecutable`; `ExecutedExecutable` wraps exactly that digest. Linux sets
mode `0755`; Windows remains unsigned and makes no Authenticode claim; macOS
applies and verifies only the ad-hoc, no-timestamp `codesign --sign -` repair
required for a runnable mutated Mach-O. It has no Developer ID identity,
entitlement, hardened-runtime, container, notarization, stapling, or
distribution-assessment authority. The final byte count and SHA-256 are bound
to native inspection and execution for every applicable target. The macOS x64
rejection is never counted as a pass and does not widen the public operation.

That handoff is not an unspecified public callback. It is the closed
`effect-build/node-target-finalizer@1` capability used only by repository
certification and release-artifact matrix jobs. One digest-bound private CI
input artifact carries the constructed bytes to the one runner whose system
target exactly matches the request; one private output artifact carries the
final bytes, and one coordinate-named receipt artifact carries the
assembled/executed receipt. The
capability has no v0.5 public export, no provider choice, and no fallback.
Ordinary library calls do not claim to return a cross-target
`AssembledExecutable` outside this controlled job.

The construction job writes one canonical `effect-build/assembler-offer@1` as
the coordinate-named sidecar beside the constructed bytes in the private input
artifact. It binds the run, coordinate, main and base identities, deterministic
contained filename, byte count, SHA-256, and input-artifact name, but it does not
claim the wrapper's later-assigned ID, digest, or expiry. After authoritative
REST observation and exact-target host admission, the finalizer downloads the
artifact and requires exactly those two top-level regular files. It strictly
authenticates the offer and the constructed file's name, length, and SHA-256—no
directory, link, duplicate, unsafe path, or extra entry—then combines the offer
with the REST fields into the local canonical request before finalization. The
request remains out of band from the input artifact whose wrapper properties it
binds.

The output artifact has the exact one-file law for its deterministic finalized
filename, byte count, and SHA-256. After uploading and reobserving it, the job
writes the canonical receipt as the sole file in a separately
coordinate-named receipt artifact. The receipt binds the output artifact but
does not claim its own later-assigned wrapper properties. One dependent
aggregation job lists all coordinate-named receipt artifacts and validates their
REST records, canonical receipts, all three exact layouts, content identities,
and authoritative run/job records before embedding each receipt in compatibility
evidence. No matrix child shares an offer or receipt output key.
GitHub artifact transport is byte-only: its extracted mode is never evidence.
The target runner restores `0755` after input validation on Linux and macOS
before finalization, inspection, or execution; Windows has no transported mode
claim. The receipt binds that target-derived mode separately from the byte
digest, and every downstream download must restore and verify it before
execution, packaging, or publication.

The current assets-capable, host-inferred Node API is provider-native only. Its
v0.5 name is `effect-build-node-sea/Raw`. Portable assembly is
`effect-build-node-sea/NodeMainExecutable`.

## Generation canon

A provider produces into a private root. effect-build observes one contained,
regular-file-only `TreeSnapshot`, then seals an immutable
`DirectoryGeneration`. The on-disk form is:

```text
current.json
generations/
  sha256-<manifest digest>/
    manifest.json
    tree/
      ...
```

Portable generation paths are slash-separated ASCII components matching
`[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9_-])?`. Absolute paths, empty
components, dot segments, backslashes, links, Windows reserved device basenames
with or without extensions, components ending in a dot or space, and
ASCII-case-insensitive collisions are rejected. Files sort by unsigned UTF-8
bytes of the normalized path.

`manifest.json` uses protocol `effect-build/generation-manifest@1`. Its exact
field order is `protocol`, `subject`, `files`. Every file has `path`, `bytes`,
`digest`, and `mediaType` in that order. Byte counts are canonical unsigned
decimal strings. A digest is `{ "algorithm": "sha256", "value": "<lowercase 64-hex>" }`. `mediaType` is always present and may be `null` only for an
unprofiled tree. A non-null value must match the exact lowercase grammar in the
machine contract, with only an optional exact `; charset=utf-8`; inputs are
rejected rather than normalized. JSON is compact UTF-8 without a BOM and has
exactly one final LF. Unknown fields are rejected. Golden bytes and their digest
are checked by the architecture suite.

`current.json` uses protocol `effect-build/current-generation@1` and contains
only `protocol` plus the manifest digest. The generation directory name is
derived from that digest, so there is no second identity field that can
disagree. Activation atomically replaces only this small reference.

A reader:

1. reads and byte-canonically decodes `current.json` once;
2. derives and pins exactly one generation without retry or fallback;
3. verifies canonical manifest bytes, digest, and derived directory identity;
4. lends only listed, contained files whose byte count and digest match; and
5. redirects new root navigation to a generation-qualified URL.

An already-open page remains on its old generation, so a lazy import cannot
cross into the newly activated generation. Garbage collection is never
automatic in v0.5.

## Lifecycle

Hard cancellation belongs only to schema-serializable portable jobs. Functions,
plugins, callbacks, and native handles are rejected before that work begins. A
portable job owns a POSIX process group or Windows Job Object before provider
work. Serialized control messages and captured stdout/stderr are each bounded at
1 MiB. Interruption sends a cooperative request, waits 5,000 ms, force-terminates
the whole owned tree, awaits confirmed exit, and cleans private staging before
returning. This is lifecycle containment, not a security sandbox.

Native provider operations retain their provider-specific semantics. Watch
delivery holds at most one completed result, replaces it with the newest result
while recording how many were superseded. Within one watch-stream instance,
including superseded events, there is at most one live build, watcher, and result
resource, at most one outstanding close per kind, and at most three outstanding
closes total. Every close is awaited exactly once; cleanup failure stays in
Effect Cause alongside any primary failure.

## Stop conditions

Stop rather than add a provider registry, generic build algebra, generic
deployment manager, generic release graph, runtime fallback, arbitrary browser
closure, mutable directory transaction claim, or hard-cancellation claim for
native callback APIs. The closed `effect-build-apple` mechanisms are not a
generic deployment manager; product and publication policy remain outside them.
Narrowing an intended evidence set requires an explicit
contract revision; it never happens silently.
