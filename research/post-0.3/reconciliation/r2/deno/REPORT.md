## Bundle modes, checking and output topology

Host `Deno.bundle()` supports multiple entrypoints, format, platform, package handling/externalization, splitting, inline imports, source maps, minification, and memory versus filesystem publication. In memory mode structured output files carry path/hash/bytes/text. In write mode publication is provider-direct, never implicitly atomic.

The selected `deno bundle` lane has different authority: selected executable, initial cwd, project/config/import-map/lock/npm resolution and process lifetime. HTML entrypoints require an outdir. `--check` is a pre-bundle type-check sub-operation. `--declaration` performs separate graph/type-check work and rolls re-exported declarations per entry. That topology is not the same as transpile declarations.

Selected-command watch is a scoped process. Internal use of esbuild context/rebuild does not create a typed `Ready`/`Rebuilt` public protocol.

## Transpile and declarations

`deno transpile` is not bundling. One input without output selection emits JavaScript to stdout. Multiple inputs require direct output topology. Separate source maps are invalid in stdout mode.

Declaration mode builds a module graph with npm resolution, invokes the type checker, rejects mixed compiler-option scopes, and writes emitted declaration files. Under outdir, relative declaration structure is preserved. These provider semantics must not be normalized into bundle declaration roll-up.

## Project, import-map, lock, npm, environment and cwd authority

Selected-command operations preserve the selected Deno executable and `initial_cwd`. Shared compile arguments include explicit config/no-config, import map, lock/no-lock/frozen lockfile, npm/node_modules controls, reload/cert and related resolution. Transpile resolves compiler options from configuration scopes.

Environment may affect caches, registries, certificates and explicit development overrides. It belongs to selected-command evidence/configuration, not a provider-neutral build algebra.

## Permission analysis and historical contradiction

The historical 2.9.3 receipt observed behavior inconsistent with the then-assumed permission boundary. It remains a falsifier but cannot be projected onto v2.9.5.

Current v2.9.5 declarations state read access for local entrypoints/dependencies, import access for remote modules and write access for filesystem output. Current tagged implementation carries the caller `PermissionsContainer`, labels host graph preparation as `Deno.bundle()`, checks later local reads/import specifiers, and supplies write checks to the host result writer. The directly selected `deno bundle` path remains trusted CLI authority for source reads.

This resolves the **source/declaration contradiction**, not runtime certification. Exact deny/no-prompt/read/import/write execution is still required.

Compile-time trusted reads and permission policy embedded into a compiled program are separate authorities.

Never key Deno solely by `2.9.5`. Retain at minimum selected executable content identity, version, release channel where observable, build/source revision or acquisition provenance, lane, host OS/architecture, requested compile target, relevant option mode and helper/runtime relations.

## denort selection, cache, download, override and offline law

`deno compile` has an explicit runtime-acquisition sub-operation:

1. consult explicit development `DENORT_BIN`;
2. otherwise derive denort archive from engine and requested target;
3. derive release path from channel identity (canary git hash; otherwise release version);
4. read DENO_DIR download cache when present;
5. otherwise download from `dl.deno.land` and atomically cache the archive;
6. unpack target denort and append standalone data;
7. publish the completed executable.

There is no truthful “silent offline fallback” state. Missing cache causes acquisition. Exact no-network/cached-only/offline outcomes remain empirical.

The override does not authorize arbitrary runtime substitution. R3 must observe its bytes and relation to target/engine/provider policy.

## Compile targets and host/target/architecture distinction

The v2.9.5 parser lists exactly six target triples:

- `x86_64-unknown-linux-gnu`
- `aarch64-unknown-linux-gnu`
- `x86_64-pc-windows-msvc`
- `aarch64-pc-windows-msvc`
- `x86_64-apple-darwin`
- `aarch64-apple-darwin`

These are advertised capabilities, not certified cells. The build **host** owns the selected Deno command, cache, network, filesystem and helper environment. The requested **target** selects denort and output format/architecture. Cross-compilation is a relation, not replacement of host identity by target identity.

Exact execution must establish host→target cells, npm/native dependency target relations, and any target-specific correctness finalization.

## Embedded permissions, includes/assets and runtime API availability

Compile embeds explicit includes and selected workspace/npm material into a standalone VFS. This is Deno-specific executable topology.

Current v2.9.5 denort deliberately has no operational `Deno.bundle()` provider: the default provider returns an explicit unavailable-in-compiled-binaries error. The imported Deno 2.9.3 execution independently observed compiled-runtime unavailability. Therefore reject a compiled-runtime bundle operation unless future exact provider evidence changes the capability.

No stronger claim is made for every other Deno runtime API. Probe only runtime capabilities required by a selected executable/profile contract.
