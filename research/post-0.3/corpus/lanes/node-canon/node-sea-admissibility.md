# Node SEA admissibility

## Scope and terminology

This document distinguishes four different propositions that are often collapsed:

1. **The SEA CLI accepts a configuration.**
2. **The preparation data or executable is produced.**
3. **The injected main can load everything it expects at runtime.**
4. **The final file is a validated, distributable executable for the requested target.**

Only the fourth proposition is a durable executable result. A syntax check or successful SEA command does not establish all four.

## Official current Node SEA domain

**UPSTREAM-DIRECT — Node v26.7.0.** Node documents SEA as an active-development feature that executes one embedded CommonJS or ESM script. The built-in `--build-sea` configuration includes `main`, `mainFormat`, an optional selected Node `executable`, `output`, warning policy, snapshot policy, code-cache policy, execution arguments, argument extension policy, and an asset dictionary. [NODE-SEA-26]

### Format

- `mainFormat: "commonjs"` selects the special injected CommonJS environment and is the default.
- `mainFormat: "module"` selects the injected ESM environment.
- ESM and CommonJS are not interchangeable annotations. Their main detection, globals, resolution, and dynamic-loading semantics differ.
- `mainFormat: "module"` cannot be used with `useSnapshot: true`.

### Loader

**UPSTREAM-DIRECT.** The injected loader does not read ordinary modules from the filesystem by default. `require()`, static `import`, and ESM `import()` can load built-ins. A filesystem/package load fails unless the application deliberately creates a filesystem-backed `require` with `module.createRequire()`. The injected CommonJS `require` is not ordinary `require`; among ordinary properties it exposes only `require.main`. ESM `import.meta.resolve` is unsupported. [NODE-SEA-26]

This means a successful Node bundle intended for `node app.js` is not automatically a valid SEA main. Ordinary Node execution has the package/filesystem resolution described in the CJS, ESM, and packages manuals; the injected default loader intentionally has a narrower domain. [NODE-CJS-26] [NODE-ESM-26] [NODE-PACKAGES-26]

### Binary identity and version

**UPSTREAM-DIRECT.** Node states that the Node binary used to produce the preparation blob must have the same version as the binary receiving it. Cross-platform creation requires snapshots and code cache to be disabled because those representations are host/platform-sensitive. [NODE-SEA-26]

**INFERENCE.** A portable assembler must make the builder/base relation explicit and verify it before provider work. An exact semantic version string is the public minimum. The selected binary's identity/path/digest can remain assembler-private, but the final target agreement must prevent substitution with a different release or target.

### Snapshot

**UPSTREAM-DIRECT.** With `useSnapshot`, the main executes while the preparation data is created, not as the ordinary launch-time main. It must arrange a deserialize main function through V8's startup-snapshot API. ESM is excluded. [NODE-SEA-26]

**INFERENCE.** Snapshot mode is a different application lifecycle and cannot be an optional bit on the smallest `NodeMain` without reintroducing major illegal combinations. It belongs to a separate assembler request/profile.

### Code cache

**UPSTREAM-DIRECT.** Code cache is generated by compiling the main during SEA preparation. Node documents that `import()` does not work when code cache is enabled. [NODE-SEA-26]

**PROPOSAL.** Fix `useCodeCache: false` in the strict portable profile. This removes a format/loading branch from every producer and consumer. A future startup-optimized profile can expose code cache with an explicit no-`import()` invariant and host/target constraints.

### Assets

**UPSTREAM-DIRECT.** Assets are a key-to-path dictionary read during SEA creation and exposed to the injected script through `node:sea` methods. They are not ordinary relative files and do not become module-resolution roots. [NODE-SEA-26]

**INFERENCE.** A producer that emits an asset file has not satisfied an asset-free main. It has produced a main plus resource graph. Mapping those assets into SEA requires stable asset keys, authenticated contents, code that consumes `node:sea`, and possibly source rewriting. That is a distinct composition.

### Native addons

**UPSTREAM-DIRECT.** Node's documented SEA pattern embeds a `.node` addon as an asset, writes it to a temporary file, then loads it with `process.dlopen()`. Node documents a Linux arm64/postject caveat. [NODE-SEA-26]

**INFERENCE.** Native addons require target OS, architecture, ABI, extraction, cleanup, and trust decisions. They are outside the smallest platform-neutral main profile.

### Signing and distributability

**UPSTREAM-DIRECT.** The current built-in flow documents signing the generated binary on macOS and an optional Windows signing path. The underlying process is explicitly subject to change. [NODE-SEA-26]

**PROPOSAL.** `NodeMain` contains no signing state. The assembler owns signing capability, credentials, platform rules, verification, and publication readiness. It must not call an unsigned candidate a validated durable executable where the target policy requires signing.

## Strict portable SEA subset

The recommended assembler contract consumes only the following subset:

| Dimension | Strict value | Reason |
|---|---|---|
| Main count | exactly one | SEA embeds one script; avoids chunk graph |
| Role | direct main | main behavior differs from imported behavior |
| Format | explicit CJS or ESM | loader/global semantics differ |
| Loader closure | finite literal built-ins only | exact default-loader intersection |
| Dynamic `import()` | none | removes code-cache and analysis branch |
| Packages/local modules | none at runtime | default loader cannot resolve them |
| JSON modules | none at runtime | must be inlined into JavaScript |
| Assets/auxiliary build files | none | separate resource-graph profile |
| Native addons | none | target/extraction/ABI semantics |
| Snapshot | false | different lifecycle; ESM conflict |
| Code cache | false | dynamic-import restriction and platform coupling |
| Exec arguments | fixed assembler policy | not producer semantics |
| Node release | exact negotiated release | parser/API/SEA/binary relation |
| System target | exact negotiated target | final executable identity |
| Content | authenticated borrowed snapshot | no unverified path/TOCTOU |

## Admissibility predicate

**PROPOSAL.** A value is admissible to the strict assembler only when all of the following are true:

```text
known protocol and profile major
and role == main
and format is accepted by the assembler offer
and agreement identity exactly matches
and borrow is live
and acquired byte length and SHA-256 match the descriptor
and exact offered Node parses the bytes in the selected format
and producer has sealed the finite-literal-builtins-only closure
and every normalized builtin exists in the offered Node inventory
and no non-builtin, local, package, JSON, addon, chunk, asset, or opaque load remains
and SEA policy is snapshot=false, codeCache=false, assets=empty
and builder/base executable relation is accepted
and destination preconditions are valid
```

The syntax clause is necessary but deliberately not sufficient.

## Why regex import scanning is not proof

Regex cannot reliably distinguish comments, strings, templates, escaped syntax, nested syntax, parser recovery, transformed code, or all import forms. More importantly, code loading can be expressed without a lexical `import` token:

- computed `require(name)`;
- aliased `require`;
- `module.createRequire()`;
- ESM `import(expression)`;
- `eval()` or `new Function()` producing a loader call;
- `process.getBuiltinModule()` or `process.dlopen()`;
- plugin-generated runtime helpers;
- source-relative `fs` reads used as implicit assets.

An AST improves lexical classification but cannot prove arbitrary dynamic behavior. The strict profile therefore combines restricted producer configuration, output-set validation, parser-based final-code checks, explicit rejection of opaque loading constructs, and a producer adapter's sealed semantic claim. A malicious or incorrect adapter can still lie; protocol types do not create a security boundary.

## Why `node --check` is not proof

**UPSTREAM-DIRECT.** `node --check` syntax-checks a script without executing it. [NODE-CLI-26]

It does not establish:

- SEA format selection;
- default-loader closure;
- package condition resolution;
- JSON attributes;
- built-in API availability;
- `import.meta`/`__dirname` behavior after injection;
- asset presence;
- native-addon ABI;
- code-cache/snapshot legality;
- exact binary compatibility;
- target architecture;
- signing;
- main-entry behavior;
- runtime success.

## General SEA versus canonical `NodeMain`

Node SEA's official domain is intentionally broader than the proposed canon. The canon is the smallest truthful intersection that an unchanged consumer can assemble without acquiring a package graph or branching into assets, snapshots, addons, and signing recipes. Direct `effect-build-node-sea/Command` must preserve the full official provider surface independently.
