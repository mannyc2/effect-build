**Overall verdict:** the constrained design mostly holds. The load-bearing moves are: two new unforgeable states (candidate, validated), a four-field bundle artifact, one cell Scope with the staging slot shared between SEA and the existing atomic-output module, a SyntaxTarget/ExecutionTarget split, and pluralizing the tool record. Reject: a Published state, ResolutionTarget as a type, any universal producer adapter, ESM admission at the bundle stage, failFast, rollback, and publish modes.

## Q1 — Split at the seams of modules you already have; only two new states pay rent

The split should be: prepare = the existing atomic-output acquisition plus provider-table lookup; execute = the existing process-ownership module (or esbuild+SEA); validate = the existing pure byte inspection plus optional digest; publish = atomic rename. The engine keeps only what is genuinely its own: matrix preflight and the bounded collect-all fold. The rent for the split itself is concrete: the SEA pipeline reuses validate and publish verbatim instead of either copying inspection-and-rename or growing the 509-line engine a second execute path behind a mode switch.

Two explicit states earn their keep, provided their constructors are not exported:

- **CandidateExecutable** (output of execute): removes the invalid state "inspect or hash a path no completed process wrote."
- **ValidatedExecutable** (output of validate, sole input type of publish): removes "publish uninspected bytes." This is the one that matters most, because SEA's execute is structurally different and the only thing forcing it through inspection is publish's input type.

Rename wrappers to reject: a **Prepared** state (it is exactly the staging handle the atomic-output acquisition already returns — naming it again is a peer representation); a **Published** state (publish's output *is* the public Artifact; a distinct internal type duplicates it and creates "which one is authoritative" ambiguity); a **Digested** state (digest is optional, so a state would fork the downstream into two peer types — it is an `Option` field on ValidatedExecutable).

## Q2 — Four facts, and the artifact's existence encodes the rest

- **`path`** — scope-local physical detail. SEA config needs a file path for `main`. Carry exactly one locator; a resident byte buffer alongside it is a peer representation of the same content and pays nothing (hash by streaming from the path).
- **`format`** — statically encoded, and I'd challenge the "ESM or CommonJS" constraint: as of the pinned Node lines you can actually test today, SEA's main script must be CommonJS. Admitting ESM at the bundle stage creates a representable-but-unconsumable artifact whose failure surfaces inside the shipped executable, after publish. Narrow the constructor to CJS and keep format as a type-level literal so a future Node ESM-SEA is a type widening, not a runtime discovery.
- **`syntaxTarget`** — statically encoded at bundle time, consumed by a dynamic cross-check in `NodeSea.createExecutable` against the pinned Node's version. Rent: removes "bundle lowered for node22 syntax embedded into a node20 binary," which throws only when the end user runs the executable.
- **`assets`** (name → scoped path, possibly empty) — scope-local physical plus statically encoded names; SEA's config consumes it directly. Rent: removes "code calls `sea.getAsset('x')` but the blob has no asset x." If the constrained pipeline actually admits no assets, drop the field entirely — an always-empty map fails the rent test.
- **esbuild stage record** (version, resolved options, entrypoint) — durable provenance. Rent is ownership, not control flow: without it, final artifact assembly must reach back into the Esbuild module to reconstruct what ran, or the receipt silently loses the stage that determined the JS semantics.

Dynamically validated at construction, carried as no field at all: exactly-one-output, no unaccounted non-built-in externals, no unanalyzable dynamic imports (esbuild reports these; treat them as failures). The artifact's existence encodes that these checks passed. Reject: `platform` (can hold only "node" — an invariant of the module, not a field), the externals list and the metafile (no consumer branches on them; keeping them is a peer representation of facts already reduced to pass/fail), a bundle digest (no cache, no CAS, no verifier — nothing consumes it), size, and any `valid/released` flag (the Scope owns lifetime; a flag manufactures the stale-artifact state it claims to track).

## Q3 — One cell Scope; the SEA candidate lives in the existing staging slot

One Scope per cell, matching the existing lifecycle. Inside it, in order: acquire the final staging slot from the existing atomic-output module (release = idempotent delete-if-present; commit = rename); `Esbuild.bundleScoped` acquires a temp workspace (release = recursive delete) and returns an artifact that *requires* the caller's Scope rather than closing its own; SEA runs; validate; rename; scope closes.

The one invalid state to design against is use-after-free: if the bundle artifact were produced inside its own `Effect.scoped` and returned, its file would be deleted before SEA reads it. Requiring Scope in `bundleScoped`'s type and never self-scoping it makes that unrepresentable. Per-stage early-closing scopes pay no rent here — peak temp footprint is roughly the bundle plus the blob plus one Node-binary copy, and eager success-path cleanup buys nothing while reintroducing the lifetime question. Reject it.

One concrete unification: SEA's copied Node binary *is* the candidate executable, so write it directly into the staging slot the atomic-output module already owns and inject the blob in place. That removes a duplicated staging workflow and the ownership ambiguity of two temp directories each holding "the executable." Atomicity is untouched: rename remains the sole commit point, it happens before scope close, the destination is only ever a rename target, and the post-rename release finds nothing to delete. Interruption is the same path as failure — the process-ownership module kills children, then finalizers run.

One challenge to a stated invariant: the cell lifecycle assumes "one scoped CLI child," but SEA execute is a *sequence* of owned child steps (blob generation, injection, and on darwin — your host — signature removal and re-signing). Extend the process-ownership module to sequential children within one cell rather than letting `NodeSea` grow its own spawn loop; otherwise you duplicate the ownership workflow you already built.

## Q4 — Two target types are new and load-bearing; one protocol deserves a name

**SyntaxTarget** and **ExecutionTarget** are demanded, and demanded *as a pair*: the operation that needs both is the Q2 compatibility gate. This seam is newly possible — Bun and Deno bundle internally with matched syntax, so the mismatch was previously unrepresentable; esbuild-then-SEA is the first place it can exist. **SystemTarget** already exists as the Artifact's canonical native target; the only change is that SEA *observes* it (host plus byte inspection) rather than *selects* it from a table — so SEA's plan should have no SystemTarget parameter at all, because a parameter would represent cross-compile requests SEA cannot honor. **ResolutionTarget** fails the rent test: it is the constant "node," nothing branches on it, and naming it is a peer representation of one esbuild option value. Record it as provenance; do not make it a type.

On producers: yes, esbuild in-process and Bun/Deno/SEA-steps as owned CLI children — and this proves *fewer* than two named protocols. The CLI protocol already exists (the process-ownership module); SEA adds invocations, not protocol. The in-process side has exactly one member and no plugin system or future consumers to serve, so an `InProcessProducer` interface is a rename wrapper around "a function returning a scoped artifact." A universal adapter is worse than unnecessary: it would force each side to stub the other's half (a diagnostics array that is always empty for CLIs, a process handle that is always absent for esbuild), which is manufactured invalid state plus two peer representations of errors. Note the distinction is API shape, not process topology — esbuild's JS API runs a native service child internally, yet presents structured results with no process for you to own. The real convergence point is the one Q1 already established: both feed ValidatedExecutable and a stage record.

## Q5 — Pluralize the stage record; version the receipt now; gate everything else on observable consumers

The singular tool record cannot describe SEA without lying — the bytes have two producers, and whichever one you name loses the other. Replace it with a non-empty *ordered* list of stage records (tool, version, role, and that stage's statically encoded facts: format and syntaxTarget for esbuild; Node version, `useSnapshot`, `useCodeCache` for SEA). Bun and Deno become honest one-element lists. Reject keeping a singular `tool` alongside a `stages` list — that is a peer representation with an authority ambiguity. Version the receipt schema in this same release: multi-stage records are the first user-visible shape change, and a missing version field is the one omission you cannot retrofit for old readers. Receipts record observations, never promises — no hermeticity or reproducibility claims, and on darwin the signing step alone makes byte-reproducibility false. One flag: if the Artifact's `bytes` is a resident content buffer rather than a size, SEA (an entire Node runtime, ~100 MB) makes it an expensive peer representation of the published file — make it a size or drop it.

Three identities, never conflated: **same semantic request** = equal SemanticPlan (entrypoint, format, syntaxTarget, requested Node, assets, output name); **same invocation** = equal BoundExecutionPlan (semantic plan plus discovered bindings: resolved Node binary and version, esbuild version, host SystemTarget); **same output bytes** = equal digest, the only byte-level claim anywhere. Equal bound plans do not imply equal digests (sources change; signing is non-deterministic), and equal digests do not imply equal invocations. The plan split's rent: without it, either the semantic layer leaks machine-local absolute paths (scope-local physical detail escaping its taxonomy bucket) or the receipt cannot say which Node actually ran.

Promotion gates, each observable: public byte inspection when a consumer outside the internal validate stage demands it; public JavaScriptBundleArtifact only when a public operation's *result* is the bundle (today it is scope-bound, and exporting a value users can hold past its Scope is handing out the use-after-free state Q3 eliminated); public receipts now, with the SEA release; SemanticPlan stays internal — upholding your own "no public stable plan" constraint — until a second producer of the same plan or a persist/replay need exists; BoundExecutionPlan is internally proven when your own test suite drives a fake executor from it, and goes public only on an external consumer; "replaceable executors" as a formal interface waits for a second interchangeable implementation *within* a protocol, which Q4 argues will not be a universal one.

Push-backs, each with the rent it refuses to pay: **failFast** removes no invalid state — it adds a second matrix completion semantics, making cell coverage in receipts mode-dependent, doubling the behavior you must test against the existing collect-all-with-independent-commits contract. **Rollback** *creates* an invalid state class: independently committed destinations that appear and then vanish, after external readers may have seen them, plus a new obligation to remember and restore prior destination contents. Atomic rename's contract — each destination is either old/absent or new-and-complete, forever forward — is the whole point; keep it. **Publish-mode switches** multiply terminal states per mode while removing none; the only legitimate member of that family, no-clobber, is a precondition, and you already own the place preconditions live — matrix preflight — so express it there or not at all. Dry-run's honest form is an operation that stops at ValidatedExecutable, which no real consumer has demanded; don't invent one.
